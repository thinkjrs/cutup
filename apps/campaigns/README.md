# Campaign allocation app

A sample app for [cutup](../../README.md) that splits an ad budget across platforms. The same Rust allocation code runs either on Vercel's servers, as native serverless functions, or in the visitor's browser, as WebAssembly. None of it is published with the crate.

## Layout

```
apps/campaigns/
  Cargo.toml    the native functions' package, and the workspace
  api/          allocate.rs and platforms.rs: the functions, one [[bin]] each
  engine/       shared Rust: a JSON request in, a JSON reply out
  wasm/         the engine for the browser, with wasm-bindgen
  data/         the sample: six platforms' daily totals
  fixtures/     requests and their replies, for the parity check
  vercel.json   the functions' runtime, vercel-rust
  package.json  the frontend, a Next.js app
  app/          its page
  components/   the form, the results and the charts
  lib/          the engines, requests, and what the charts show
  lib/bindings/ the request and reply types, generated by ts-rs from the engine
  public/       the browser engine's worker, and its wasm once built
  scripts/      build-wasm.sh, which builds the browser engine
```

## The model

Each ad platform is an asset, and the weights are shares of the budget.
- **Returns:** for each metric, impressions, clicks, link clicks or views, a platform's return on a day is how far what a unit of spend bought there is above or below its average over the request's platforms and days, as a share of the average: 0.05 is 5% more, −0.05 is 5% less. So the returns are near 0, and a run of days below the average is a drawdown.
- **One allocation per metric:** every method allocates once for each metric.
- **Days:** only days on which every chosen platform spent count.
- **Saturation isn't modeled:** these methods take results to grow in proportion to spend.

The sample has six platforms' daily spend, impressions, clicks, link clicks and views, from 2025-09-01 to 2026-09-30. Every volume is scaled by the same constant, so each yield per unit of spend is the real one and the absolute amounts aren't.

## Requests and replies

`POST /api/allocate` and the wasm `allocate` take the same JSON request:

```json
{
  "platforms": ["Meta", "Google", "TikTok"],
  "from": "2026-01-01",
  "metrics": ["clicks", "link_clicks"],
  "method": {"name": "min_variance", "bounds": {"upper": 0.6}},
  "rolling": {"window": 60, "step": 7}
}
```

- **Defaults:** everything but `method` is optional. The platforms default to Meta, Google and TikTok, the three that spent on every day, and the metrics to all four.
- **Methods:** a method is cutup's own JSON with a `name`, such as `{"name": "mean_variance", "risk_aversion": 5.0}`, `{"name": "min_mad", "downside": -0.1}` or `{"name": "min_cdar", "confidence": 0.9}`. A frontier, `"frontier": 10`, takes a mean-variance method.
- **Statistics:** each result has the expected return, volatility, Sharpe ratio, diversification ratio and risk shares, then CVaR, the mean absolute deviation, the mean shortfall below the average, CDaR, and the maximum and average drawdowns. CVaR and CDaR are at 95%.
- **Replies:** a response, with each metric's weights and statistics or its own error, comes with status 200. A request that isn't JSON for one is 400, and one that can't be allocated is 422. Both come as `{"error": ..}`.

`GET /api/platforms`, and the wasm `platforms`, list the sample's platforms, each with its first and last dates and how many days it spent on.

## The frontend

One page: a request on the left, its results on the right, and the sample's weekly yields below.
- **Two engines:** a switch picks the server, which posts to `/api/allocate`, or the browser, which runs the wasm build in a Web Worker. The worker starts when the browser engine is picked, so its first run's round trip doesn't include loading the wasm, and a visitor who never picks it never downloads it. Both get the same request text, and the results say which answered, how long the round trip took, and how long the engine took. The server's time comes in a `server-timing` header.
- **The request:** the form covers the platforms, dates, metrics, method, a cap on each platform's share, a mean-variance risk aversion and frontier, min CVaR's and min CDaR's confidence, min MAD's shortfall threshold, and rolling windows. The JSON it makes can be edited for any of cutup's other settings, and is sent as it's written.
- **The results:** each metric's weights side by side, their statistics, then their losses and drawdowns, the efficient frontier and the weights over time when asked for, each with a table view.
- **Exports:** the whole run as JSON, with the request, the engine and its timing, and every allocation as CSV, one row per metric and window.
- **The types:** `lib/bindings` holds ts-rs's TypeScript for the engine's requests and replies, committed so the frontend builds without Rust. An engine test fails when they're stale.

## Development

From `apps/campaigns`:

```bash
# Format, lint and test everything natively
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

# The engine's and the wrapper's tests on wasm, the parity check included
CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER=wasm-bindgen-test-runner \
  cargo test --target wasm32-unknown-unknown -p campaign-engine -p campaign-wasm

# Print each metric's allocation for a few methods
cargo run -p campaign-engine --example sample

# The frontend: install, then check formatting and types, and test
yarn install
yarn format:check
yarn typecheck
yarn test

# Build the browser engine into public/wasm, then serve the app
yarn dev
```

- **Bindings:** after a change to the engine's types, regenerate `lib/bindings` with `UPDATE_BINDINGS=1 cargo test -p campaign-engine bindings`.
- **Parity:** `fixtures/requests.json` holds requests, and `fixtures/replies.json` their replies. The engine's tests check every reply natively and on wasm, to 1e-14, since `ln` can differ in the last bit between the two. After a change that moves the replies, regenerate them natively with `UPDATE_FIXTURES=1 cargo test -p campaign-engine parity`.
- **Builds:**
  - The native functions build with `cargo build --release`.
  - `yarn wasm`, which `yarn dev` and `yarn build` run first, builds the browser engine with `scripts/build-wasm.sh`: the wrapper with the `wasm-release` profile, which optimizes for size, then the `wasm-bindgen` CLI at the version in `Cargo.lock`, then binaryen's `wasm-opt`. It fetches what it needs and doesn't find: Rust through rustup, and prebuilt `wasm-bindgen` and binaryen into `.tools`. So Vercel's build runs it as it is. Before `wasm-opt`, the wasm comes to about 300 KB gzipped, with the sample in it.
  - The native functions need Rust 1.88 for `vercel_runtime`. The engine and the wrapper keep cutup's 1.85.
- **Running locally:** `vercel dev` runs the functions and the app together. Under `yarn dev` alone, `/api` doesn't answer, so the app switches to the browser engine and says so.
- **Vercel:** the project's root directory is `apps/campaigns`, with the Next.js preset. The app has no API routes of its own, so `/api/*` is left to the Rust functions.
